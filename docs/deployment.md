# Доставка и сбор отчётов: пример сценария

Пример сценария: как разослать чекер на серверы и собрать отчёты имеющейся
инфраструктурой управления. Для примера использован агент Kaspersky Security
Center; подойдёт любой канал «доставить файл → выполнить команду → забрать
файл»: консоль управления, Ansible, ssh/scp и т.п.

Чекер: один файл `securelinux-audit.sh` (+ `securelinux-audit.sh.sha256` для
контроля целостности). Он только читает конфигурацию системы и печатает отчёт
в стандартный вывод: сам ничего не отправляет и не изменяет на хосте. Формат
`pdf` отчёт оформляет сам чекер: на сервере не нужны ни офисный пакет, ни
дополнительные библиотеки (достаточно `python3`, который нужен и для проверок).

## 1. Проверка целостности до раздачи

```bash
sha256sum -c securelinux-audit.sh.sha256
# ожидаемый ответ: securelinux-audit.sh: OK
```

## 2. Модель развёртывания

1. В консоли управления создаётся задача: доставить `securelinux-audit.sh`
   на целевые серверы (например, в `/tmp` или рабочий каталог агента).
2. Агент выполняет команду запуска от root; stdout перенаправляется в файл
   отчёта. Имя файла: с hostname и датой, чтобы отчёты с парка серверов
   не смешивались.
3. Файлы отчётов собираются средствами консоли и передаются администраторам
   серверов для устранения замечаний.

Тип задачи и способ выгрузки файла зависит от используемой консоли; контракт
со стороны чекера: «команда → отчёт в stdout».

## 3. Команды запуска

Скрипт: bash (`#!/bin/bash -p`); через `sh` (dash) он не работает:
запуск `bash securelinux-audit.sh …` или `./securelinux-audit.sh …`.

```bash
# основной прогон: читаемый отчёт для администраторов:
bash securelinux-audit.sh --check > /tmp/slp-audit-$(hostname)-$(date +%F-%H%M%S).txt

# оформленный отчёт PDF: генерирует сам скрипт (зависимостей сверх python3 нет;
# вывод: только ASCII-текст PDF, перенаправляется в файл):
bash securelinux-audit.sh --check --format pdf > /tmp/slp-audit-$(hostname)-$(date +%F-%H%M%S).pdf

# машиночитаемые форматы для архива (опционально):
bash securelinux-audit.sh --check --format raw  > /tmp/slp-audit-$(hostname)-$(date +%F-%H%M%S).raw
bash securelinux-audit.sh --check --format json > /tmp/slp-audit-$(hostname)-$(date +%F-%H%M%S).json

# компактный вариант: только нарушения (FAIL/ERROR):
bash securelinux-audit.sh --check --failed > /tmp/slp-failed-$(hostname)-$(date +%F-%H%M%S).txt
```

Запуск от root: часть контролей читает файлы, доступные только root (агент
обычно работает от root: sudo не нужен). Без root эти контроли дадут ERROR,
и итог станет UNEVALUATED.

## 4. Содержимое отчёта

- `SUPPORT=SUPPORTED`: система из верифицированной матрицы (Debian 12/13;
  Ubuntu 22.04 полная; Ubuntu 24.04 и 26.04 полная/минимальная);
  `SUPPORT=UNSUPPORTED`: вне матрицы, проверки всё равно выполнены.
- 85 контролей ядра ФСТЭК: `PASS` / `FAIL` / `NOT_FOUND` /
  `NOT_APPLICABLE` / `ERROR` + наблюдаемое значение.
- `POLICY_STATUS`: `COMPLIANT`: нарушений нет; `NONCOMPLIANT`: есть FAIL;
  `UNEVALUATED`: оценка не завершена (ERROR/NOT_FOUND).
- Дополнительный контроль: `--check --layer recommended`;
  список контролей без запуска: `--list`.

NONCOMPLIANT на чистой установке ОС: ожидаемый результат: настройки
по умолчанию не соответствуют требованиям, перечень несоответствий и есть
предмет отчёта.

## 5. Код возврата

| Код | Значение |
|-----|----------|
| 0 | оценка завершена полностью (итог COMPLIANT или NONCOMPLIANT) |
| 1 | оценка не завершена (UNEVALUATED) либо внутренний сбой выполнения/вывода |
| 2 | ошибка вызова (USAGE_ERROR: неверные или повторные аргументы) |

## 6. Гарантии

- check-only: чекер не устанавливает пакеты, не меняет файлы, службы,
  сетевые и системные параметры;
- аргументы вне задокументированного набора отклоняются (USAGE_ERROR, код 2);
- для полного покрытия нужен запуск от root.
